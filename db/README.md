# Database migrations

Schema changes for all three clusters live in `migrations/` and are applied by Flyway, as a separate step before any service starts. Services never migrate the database themselves.

```bash
scripts/dev.sh migrate
```

## Rules

- A migration that has been applied is never edited. Fix mistakes with a new migration.
- Every change must work with the previous release of every service still running. Deployments roll region by region, so old and new code share the same database for a while.
  - Add columns as nullable or with a default; make them required in a later migration once all services write them.
  - Rename or drop in two steps: stop using the old column first, remove it in a later release.
  - Never add a required field to a stored tenant spec.
- No foreign keys across schemas. Services in one schema learn about changes in another through the outbox.
- Each service has its own role and can only touch its own schema. A new table gets grants in the same migration, and `tests/grants_test.sql` gets a check for it.
- Ids are UUIDs generated by the application, so rows created in different regions never collide.

## Schemas

| Schema | Owner | Contents |
| :--- | :--- | :--- |
| `identity` | identity | users, tokens, login attempts |
| `platform` | broker, control-plane | tenants and their immutable versions, broker instances |

Each schema has an `outbox` table; `platform` also has a `job_queue`.
